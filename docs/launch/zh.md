## 即刻 / 微博 / X 中文

我 30 天的 Claude Code 缓存命中率 95.4%，输入花费照样有五分之一（$538）用在了缓存重建上。

Prompt Cache 的计费是不对称的：命中 0.1×（Fable 5.1 上 0.025×），重建 1.25–2×。200k 上下文漏一次等于 80 次命中，所以 2% 的调用吃掉了一半以上的全价输入，命中率纹丝不动。

更意外的是：那些宣传"token 少 60–90%"的压缩工具，减的是上下文携带量，而携带按缓存读取价计费，是账单上最便宜的一行。2,848 次真实计费的运行里，工具输出砍 38%，账单反而 +6.8%（arXiv 2607.12161）。我的账单 44% 是缓存写入，压缩器碰不到。

真正有用的是 Claude Code 自带的四个设置（压缩窗口、缓存 TTL、空闲压缩、Bash 输出上限），只是默认值不是为任何人调的。`kvleak tune` 用你自己 30 天的记录把每个候选值回放一遍，`--apply` 写进去：我这里输入花费 −45%。72 次 A/B benchmark 每个 arm 准确度都是 1.0。

一行 `uvx kvleak`，读本地已有的会话文件，不联网、零依赖、也支持 Codex CLI / Gemini CLI / OpenCode。MIT 开源 👉 https://github.com/shangliy/kvleak

## V2EX（分享创造）/ 知乎

**标题：** 开源了一个工具：Claude Code 缓存命中率 95%，为什么还有五分之一的输入花费在缓存重建上？以及"省 60–90% token"为什么不省钱

**正文结构：**
1. 反直觉的事实：命中率按 token 算，钱按「未命中 × 上下文大小」算。95.4% 命中率，20.7% 的输入花费漏掉。
2. 计费原理：读 0.1× / 写 1.25×（1 小时 TTL 是 2×），盈亏平衡 `K_max = floor((write − read) / read)`。
3. 30 天审计：贴 README 的原因拆解表（空闲超时 69%、新会话冷启动 15%、子 Agent 冷启动 5%）。
4. token ≠ 钱：贴 `kvleak whatif` 那张表，解释携带按读取价计费，账单 44% 是写入。
5. 四个设置：贴 `kvleak tune` 表，−45%；benchmark 准确度不变；一周后 `kvleak probe` 看真实前后对比。
6. 安装四条命令（README"装上"一节），每条都能撤销。
7. 欢迎把自己的数字贴到 issue #1。
