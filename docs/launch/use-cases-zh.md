# kvleak 五个实战场景

除场景四中注明「模拟」的部分外，所有数字都来自维护者本人 30 天（2026-09-21 至 2026-10-20）的真实 Claude Code 记录，按公开 API 价格计算。在你自己的机器上运行同样的命令即可复现。

---

## 场景一：月度账单体检：命中率 97.5%，为什么还漏了 27.5%？

**为什么用：** 缓存命中率按 Token 计算，钱却是按「未命中次数 × 上下文大小」花掉的。命中率看起来很好，并不代表没在漏钱。

**什么场景：** 每月月底，或者账单、限额突然变紧张的时候。

**怎么用：**
```bash
uvx kvleak --since 30d
uvx kvleak --since 30d --html report.html   # 生成可以分享给团队的报告
```

**效果（真实数据）：**
- 交互式会话命中率 **97.5%**，但 1,522 美元输入花费中有 **418 美元（27.5%）** 用在了缓存重建上。
- 只占 **2.2%** 的调用，吃掉了 **53.7%** 的全价输入。
- 最漏的一个会话命中率高达 **99.0%**，照样漏了 **82 美元**。
- kvleak 直接告诉你：**82%** 的漏损来自「空闲超过 TTL」，下一步该优化什么一目了然。

## 场景二：离开电脑前，该不该续一下缓存？

**为什么用：** 在 Fable 5.1 上，200k 上下文漏一次相当于 80 次命中的价格。离开去开会或吃午饭之前，只要发一条消息，就能把缓存寿命续上。

**什么场景：** 长上下文会话中途要离开 30 分钟到 2 小时，比如开会、吃饭、等长时间编译。

**怎么用：**
```bash
uvx kvleak statusline --install          # 在 Claude Code 状态栏显示 ◕ cache 3:41 · 452k ctx · rebuild $9.04
uvx kvleak breakeven 450k --model claude-fable-5-1 --ttl 1h --idle 85m
```
看到倒计时快结束时，随手发一句话（比如「继续」），就会免费重置 TTL。

**效果（真实案例）：**
- 一个 Fable 5.1 会话带着 **452k** 上下文空闲了 **1 小时 24 分钟**，回来后的第一条消息被迫全量重建，多花了 **8.92 美元**。
- 如果在第 59 分钟发一条消息续命，成本只有 **0.11 美元**，可以省下 **8.81 美元（98.8%）**。
- 30 天里像这样 2 小时以内、本可以续上的空闲有 45 次，合计可省 **90 美元**。

## 场景三：揪出「莫名其妙」的缓存击穿

**为什么用：** 有时你明明一直在操作，没离开过，缓存还是整个失效了。原因可能是会话中途切了模型，也可能是提示词前缀被悄悄改了（CLAUDE.md 被编辑、MCP 服务重连、hook 注入了时间戳、JSON 键顺序变了）。这类问题靠肉眼几乎查不出来。

**什么场景：** 某个会话特别贵、特别慢，想弄清是哪一步出了问题。

**怎么用：**
```bash
uvx kvleak session 5a964e68 --misses-only
```
它会逐步列出每一次未命中：时间、距上一次调用的间隔、模型、重建了多少 Token、原因。

**效果（真实案例）：**
- **前缀击穿：** 距上一次调用只有 **69 秒**，缓存却整个失效，重建了 **333k** Token，多花 **6.57 美元**。拿着这个时间点去查当时改了什么，问题就能定位。
- **切换模型：** 一个 **715k** 上下文的会话中途从 Fable 切到 Opus，因为 KV Cache 按模型隔离，这一步多花了 **5.57 美元**。如果先 `/compact` 到约 50k 再切，代价约 **0.39 美元**。
- 30 天里这两类问题合计约 **40 美元**，而且只要找到原因就能彻底消除。

## 场景四：多 Agent Swarm 省 Token

**为什么用：** 多 Agent 会把漏损成倍放大，有三个原因：
- 公共看板上贴一份完整日志，所有 Worker 在之后的每一轮都要重复读。
- 每新建一个子 Agent，都要全价加载系统提示词和工具定义。
- 缓存按模型隔离，跨模型交接就要整段重算。

**什么场景：** Swarm、Planner/Worker 架构、Best-of-N、Claude Code 子 Agent 用得很多的工作流。

**怎么用：**
```bash
uvx kvleak pointer /tmp/build.log --status FAIL --note "3 个测试失败"
# 输出约 60 Token 的指针，代替把 500 行日志贴到看板上
uvx kvleak --since 7d     # 查看「子 Agent 冷启动」的占比
```
再把 `docs/playbook.md` 里的「Token & cache efficiency contract」贴进 Swarm 的系统指令。

**效果：**
- **真实数据：** 30 天里有 127 次子 Agent 冷启动，每次平均全价加载 **28.3k** Token，合计 **27 美元**。复用常驻 Worker 可以省掉这部分。
- **模拟数据**（`python examples/swarm_sim.py`，6 个 Worker × 40 轮，按 Opus 5.5 价格）：

  | 做法 | 输入成本 | 相比原始做法 |
  |---|---:|---:|
  | 贴日志、每轮重建 Agent、跨模型审查 | $71.10 | — |
  | 看板只贴指针 | $27.37 | **−62%** |
  | 再加：常驻 Worker 复用 | $23.18 | −67% |
  | 再加：每个 Worker 锁定一个模型 | $9.63 | **−86%** |

## 场景五：给批量任务和 CI 加一道成本门禁

**为什么用：** 夜间批处理、`claude -p` 脚本、CI 里的 Agent 任务都没人盯着。一旦提示词前缀不稳定，每次运行都会冷启动，成本可能悄悄翻倍。

**什么场景：** 定时任务、批量打标签或改写、CI 中的代码审查 Agent。

**怎么用：**
```yaml
- name: Cache-efficiency gate
  run: pipx run kvleak --path ./agent-logs --markdown "$GITHUB_STEP_SUMMARY" --fail-over 15
```
漏损超过输入花费的 15% 时，任务以退出码 2 失败，报告会自动出现在 GitHub Actions 的运行摘要页面里。

**效果（真实数据）：**
- 30 天里跑了 **20,530** 次一次性的 `claude -p` 任务。其中 **74%** 复用了共享前缀缓存，另有 **901** 次冷启动，每次平均全价加载 **20k** Token。
- 这类任务整体命中率只有 **59.4%**，远低于交互式会话的 97.5%，而且漏损 **99.9%** 来自冷启动。
- 对应的改进方向很明确：保持系统提示词和工具列表完全一致，并把批量任务集中在同一个 TTL 窗口内跑完。

---

### 一句话总结

> 命中率是虚荣指标，漏损金额才是真实指标。`uvx kvleak` 用 3 秒钟告诉你：钱漏在哪、为什么漏、怎么堵。
